# HEATDEATH

[English (полная версия)](README.en.md) · [Landing page](README.md)

Офлайн-церемония для EVM recovery-фраз и Safe cold/recovery owners, критические
свойства которой можно **независимо проверить** командами.

Один читаемый файл на 300 КБ — собранный бандл без зависимостей в рантайме
(в дереве исходников их пять, все от одного автора). Генерирует 24-словную BIP-39
фразу из 256 бит энтропии и выводит адреса Ethereum. Совместим с MetaMask,
Rabby, Trust, Ledger, Rainbow — со всем, что понимает BIP-39.

Требуется Node 26 LTS (`.node-version`): сетевой scope Permission Model появился
только в Node 25, и без него команды, работающие с секретом, не запускаются.

```sh
npm ci --ignore-scripts
npm run self-test        # 22 группы проверок, включая негативные
npm run prove-sandbox    # рантайм отказывает сети, запуску процессов и записи
npm run generate:dice    # генерация
npm run verify           # сверка того, что вы записали на бумагу
```

Если вы здесь впервые — **[QUICKSTART.md](QUICKSTART.md)**, пошагово и без теории.

## Чем это отличается

Каждая строка ниже проверяется командой, а не обещанием.

| Свойство | Как проверить |
|---|---|
| **Векторы гоняются до появления секрета** | `npm run self-test`. Не сошёлся хоть один эталонный вектор — инструмент отказывается генерировать. |
| **Две независимые реализации** | BIP-39, PBKDF2 и BIP-32 CKDpriv считаются дважды: через `@scure` и через голый `node:crypto`. Расхождение = отказ. |
| **Песочница на уровне рантайма** | `npm run prove-sandbox` → `6/6 capability probes denied`. Все шесть: сеть, DNS, подпроцессы, воркеры, запись на диск и чтение за пределами каталога пакета — запрещены Node, а не совестью автора. Проба засчитывается как запрещённая только при ответе Node `ERR_ACCESS_DENIED`; отказ соединения или промах DNS на офлайн-машине показываются как *not enforced*. |
| **Многоисточниковая энтропия** | Три источника ОС плюс кубики, XOR доменно-разделённых хешей, health-тесты в стиле NIST SP 800-90B. |
| **Отказ в опасной среде** | SSH, подключённый отладчик, перенаправленные stdin или stdout — отказ. tmux, root, облачный каталог — предупреждение. |
| **`--verify` против описок** | Разворачивает сокращения от 3 букв, подсказывает исправления по расстоянию Левенштейна. Ошибка переписывания — причина потерь номер один. |
| **SLIP-39 без единой точки отказа** | `npm run split` → доли 2-of-3. 45 официальных векторов Trezor и восстановление из **каждого** допустимого подмножества. |
| **Воспроизводимая сборка и PQ-подписи** | Две сборки → один SHA-256. Манифест подписан Ed25519, ML-DSA-87 и SLH-DSA. |

## Сравнение

Полная таблица — [docs/ru/COMPARISON.md](docs/ru/COMPARISON.md). Кратко:

| Проект | Чем мы лучше |
|---|---|
| [iancoleman/bip39](https://github.com/iancoleman/bip39) | Не браузер: нет расширений, инжектящихся в `file://`, нет кеша страницы. Векторы в рантайме, кросс-проверка реализаций, песочница, проверки среды. У проекта нет пушей с 04.2024 и 226 открытых issue. |
| `cast wallet new-mnemonic` (Foundry) | Он принимает `--entropy` **аргументом командной строки** — это видно в `ps` и попадает в историю shell. Даёт 12 слов против наших 24. Ни векторов в рантайме, ни песочницы. |
| [bitcoinjs/bip39](https://github.com/bitcoinjs/bip39), [scure-bip39](https://github.com/paulmillr/scure-bip39) | Это библиотеки: у них нет политики энтропии, режима сверки и никакого мнения о среде запуска. `@scure` мы используем внутри и добавляем всё перечисленное. |
| [trezor/python-mnemonic](https://github.com/trezor/python-mnemonic) | Эталон BIP-39, но тоже библиотека: векторы лежат в тестах, а не в пути генерации. |
| [python-slip39](https://github.com/pjkundert/python-slip39) | Мы даём SLIP-39 **и** сохраняем совместимость с MetaMask, и проверяем восстановление из каждого подмножества до того, как напечатать доли. У него нет ввода с кубиков. |
| [bip_utils](https://github.com/ebellocchia/bip_utils) | Шире по монетам, но без гарантий среды, векторов в рантайме и кросс-проверки. |
| SeedSigner, Krux, Coldcard, Passport | **Здесь мы проигрываем — см. следующий раздел.** Единственное наше преимущество: кросс-проверка обязательна и непропускаема, а их сверка с третьим инструментом — ручная процедура, которую большинство пропустит. |

### Где мы проигрываем

Перечисленные ограничения структурны: они следуют из выбранной среды исполнения и
не устраняются доработкой кода. Развёрнутый разбор с измерениями —
в [COMPARISON.md](docs/ru/COMPARISON.md).

| Ограничение | Существо |
|---|---|
| **Поверхность атаки операционной системы** | Выделенное устройство выигрывает категориально. SeedSigner исполняется на плате, где радиомодули отсутствуют физически, и стирает RAM при снятии питания. Наш процесс работает в macOS с сетевым стеком, swap и системными службами. `--permission` ограничивает наш процесс и не влияет на остальную машину. |
| **Внешнего аудита нет** | Аудит проходили зависимости: `@scure/bip39` проверен Cure53 в январе 2022 при финансировании Ethereum Foundation. Сам инструмент, около 4 350 строк, внешней проверки не проходил. |
| **Кросс-проверка ограничена по природе** | Один автор, один язык, один процесс. Она обнаруживает подменённую зависимость и ошибку переноса, но не обнаружит общее заблуждение: при неверно понятом правиле деривации обе реализации закодируют одну и ту же ошибку и сойдутся. |
| **Подписание транзакций не реализовано** | При импорте сида в MetaMask на подключённой машине значительная часть полученной безопасности теряется. Ограничение не действует, если сид остаётся в аппаратном кошельке или в холодном хранении. |
| **Баг класса Coldcard остался бы необнаруженным** | Векторы проверяют путь деривации, тогда как отказ произошёл в пути энтропии. Health-тесты вывод слабого PRNG также пропускают. Обнаружение обеспечивали только кубики. |

### Что делать при крупных суммах

Генерировать сид на выделенном железе (Coldcard в режиме «только кубики», SeedSigner,
Passport), а **наш инструмент запускать офлайн в режиме `--verify`** как независимую
вторую реализацию, подтверждающую EVM-адреса. Эту же роль второму инструменту
отводит документация SeedSigner.

## Команды

```
npm run wizard           пошаговый мастер — начните отсюда
npm run rehearse:safe-owner  публичная репетиция Safe cold owner
npm run doctor           проверить готовность без создания секрета
npm run safe-owner       создать один Safe cold/recovery owner
npm run self-test        все эталонные и негативные тесты
npm run generate         новый кошелёк
npm run generate:dice    то же плюс кубики (рекомендуется); очистка экрана предлагается везде
npm run generate:account схема Ledger Live: адреса не связываются одним xpub
npm run verify           сверка фразы с бумаги
npm run split            разделить фразу на доли SLIP-39
npm run combine          восстановить фразу из долей
npm run prove-sandbox    показать отказы рантайма
npm run build            воспроизводимая сборка артефактов
npm run verify-release   проверить хеши и три подписи
```

Эти команды исполняют текущий checkout исходников и поэтому печатают предупреждение
о том, что он не проверен релизными подписями. Полный скачанный релиз запускается
соответствующей командой `:verified`, например `npm run self-test:verified`; этот
режим никогда не откатывается к исходникам.

Опции: `--dice`, `--scheme=metamask|account`, `--accounts=N`, `--shares=2of3`,
`--group-threshold=N`, `--show-public`, `--show-private`, `--wipe-screen`, `--qr`.
Мастер учитывает `--dice`, `--shares`, `--group-threshold`, `--show-public` и
`--show-private`; очистку экрана он предлагает всегда, поэтому `--wipe-screen` там отклоняется.

### `--qr` — сверка адресов без перепечатывания

Печатает список адресов QR-кодами, чтобы сравнить его с тем, что показывает
кошелёк после импорта, не набирая 42 hex-символа одиннадцать раз. Ошибка при
сверке — самый частый реальный отказ всего процесса.

**Что там никогда не окажется:** фраза, энтропия, seed, приватные ключи, доли
SLIP-39 — и расширенный публичный ключ тоже. Утечка одного account-xpub
раскрывает публичные ключи всех адресов под ним, включая никогда не тратившие
(см. [docs/ru/ENTROPY.md](docs/ru/ENTROPY.md)), а сфотографированный QR машиночитаем
в отличие от сфотографированного списка. Функция принимает **массив адресов** и
проверяет каждый по маске EVM-адреса — это структурная гарантия, а не дисциплина.

**Чем это не является.** Не независимой проверкой. Чтобы независимо проверить
деривацию, второе устройство должно её **выполнить**, а для этого ему нужен сид.
Перенос адресов переносит результат той самой вычислительной операции, которую
мы проверяем, — сам себя он не проверит. Настоящая независимая сверка описана в
[docs/ru/COMPARISON.md](docs/ru/COMPARISON.md#сверка-с-третьими-инструментами).

Секреты читаются интерактивно со скрытым эхом и **никогда** не принимаются
аргументом командной строки: argv виден любому процессу через `ps` и пишется
в историю shell.

## `npm run wizard` — пошаговый режим

Ведёт через всю процедуру за шесть шагов: проверка среды → энтропия → passphrase
→ генерация → **обязательная сверка** → резервные доли. Ничего не пропустить.

Ключевой шаг — пятый. Мастер **убирает фразу с экрана** и просит набрать её
с бумаги, после чего сверяет пословно в памяти:

```
  MISMATCH at word 5.
  Your paper is wrong; the generated phrase is correct. Fix the paper:
     5. correct: drive   you typed: abandon
```

Это сильнее ручного пути, где предлагается сверить адреса глазами — именно та
проверка, которую уставший человек делает плохо. Ошибка переписывания, прошедшая
чек-сумму BIP-39, случается примерно раз на 256 и обнаруживается через годы.

Экран очищается **только после** вашего подтверждения, что фраза записана, а
команда `show` вернёт её в любой момент. Пока расхождение не устранено, ничего
не теряется.

**Мастер не содержит собственной криптографии.** Каждая операция в нём — вызов
уже существующей функции, покрытой self-test: `assertRuntime`, `selfTest`,
`collectEntropy`, `crossCheck`, `primaryAccounts`, `splitSecretIntoShares`. Он
не может ослабить гарантии, потому что ни одной из них не реализует — он лишь
убирает возможность пропустить шаг. Приватные ключи он не печатает вообще.

## `npm run op-export` — перевалочный буфер в 1Password

Отдельная команда, которая одним действием складывает в **одну** запись
1Password всё сгенерированное: 24 слова, приватные и публичные ключи первых
трёх адресов и все три доли SLIP-39. Смысл — момент создания: не переписывать
десяток секретов руками, а перенести их дальше и **удалить запись**.

### Что нужно поставить

Интеграция требует **двух** вещей — самого приложения 1Password и его CLI:

```sh
brew install --cask 1password          # приложение, если ещё нет
brew install --cask 1password-cli      # CLI (даёт команду `op`)
op --version                           # проверка: должно напечатать версию
```

Затем **включите интеграцию в приложении**: 1Password → Settings → Developer →
«Integrate with 1Password CLI». Без этой галочки `op` не сможет достучаться до
хранилища, и команда упадёт.

Проверьте, что связка работает, до того как запускать экспорт:

```sh
op vault list
```

Приложение спросит подтверждение (Touch ID). Если список хранилищ появился —
всё готово. Токен на диске при этом не хранится: `op` ходит через приложение,
и это более безопасный путь, чем сервисные токены.

### Как пользоваться

```sh
npm run op-export:dry     # репетиция: op показывает предпросмотр, не пишет ничего
npm run op-export         # по-настоящему
```

**Начните с `:dry`.** Он проходит весь путь до конца и должен закончиться
строкой `DRY RUN succeeded - op accepted the item and wrote NOTHING`.
Последовательность вопросов у репетиции и боевого прогона одинаковая
намеренно: репетиция, пропускающая шаги, репетирует не то.

### Два режима

Команда спрашивает в самом начале:

```
new or existing?
```

#### `new` — создать кошелёк и сразу сложить его

Обычный сценарий. Заранее ничего создавать не нужно. Порядок шагов:

1. Предлагает бросить кубики (можно отказаться — будет 256 бит из источников ОС).
2. Спрашивает BIP-39 passphrase и оценивает её стойкость.
3. Генерирует кошелёк, прогоняет round-trip и кросс-проверку двумя реализациями.
4. **Показывает 24 слова и ждёт, пока вы подтвердите, что записали их на бумагу.**
5. Делит энтропию на три доли SLIP-39 и проверяет все три комбинации.
6. Складывает всё в одну запись 1Password и печатает команду её удаления.

Порядок здесь намеренный: **бумага раньше 1Password.** Запись вы удалите,
бумага остаётся.

Оговорка, которую команда произносит сама: при `new` сид рождается в процессе,
работающем на 5/6. Сгенерировать через `npm run wizard` при полных 6/6 тоже
можно — но тогда фразу придётся вводить сюда руками, а это своя порция
экспозиции. Бесплатного варианта нет.

#### `existing` — сложить уже созданный кошелёк

Для случая, когда фраза у вас уже есть. Вводите 24 слова с бумаги (ввод скрыт,
сокращения от 3 букв разворачиваются, опечатки подсказываются). Дальше всё
то же самое: passphrase, кросс-проверка, доли, запись.

Перед записью команда печатает **master fingerprint** и **адрес индекса 1** —
сверьте их с тем, что записывали при создании. Одно неверно переписанное
слово, прошедшее чек-сумму, даёт другой валидный кошелёк, и вы сложили бы
в 1Password чужой.

### Что попадает в запись

17 полей: заметка-предупреждение, 24 слова, статус passphrase, fingerprint,
путь деривации, по три поля (адрес, публичный и приватный ключ) на первые три
адреса и три доли SLIP-39. Число адресов меняется флагом `--accounts=N`.

### Как секрет попадает в `op`

Только через **stdin дочернего процесса**. Замерено на macOS:

| Канал | Виден другим процессам |
|---|---|
| `argv` | **ДА**, обычным `ps` |
| переменная окружения | **ДА**, через `ps -E` под тем же uid |
| временный файл | лежит на диске до удаления |
| **stdin-пайп** | **НЕТ** — живёт в памяти ядра |

В аргументах командной строки передаются только имя хранилища и формат вывода.
Ни одного секретного значения ни в argv, ни в окружении, ни в файле — проверено
измерением: 0 вхождений маркера в `ps` по всем процессам.

**Почему в цепочке есть `cat`.** Node отдаёт дочернему процессу **сокет**, а не
настоящий пайп, и `op` такой ввод не принимает — он отвечает
`provide the item category with '--category' flag`, что выглядит как проблема
с JSON и ею не является. Измерено:

| Способ подачи | Что видит `op` | Результат |
|---|---|---|
| `echo … \| op` | FIFO | работает |
| `op … < файл` | обычный файл | отказ |
| Node `spawn` с `"pipe"` | **сокет** | **отказ** |
| Node `spawn` + `mkfifo` | FIFO | работает |

FIFO сработал бы, но требует права на запись в файловую систему и оставляет
путь, который может открыть другой процесс. Поэтому пайп строит оболочка: наш
сокет кормит `cat`, а `cat` кормит `op` через настоящий пайп. Имя хранилища
передаётся позиционным аргументом, чтобы его нельзя было подставить в строку
команды.

### Какие векторы это добавляет — и что с ними сделано

| Вектор | Состояние |
|---|---|
| Секрет в `argv` | Устранён. Проверено: **0 вхождений** маркера в `ps` по всем процессам |
| Секрет в переменных окружения | Устранён. Проверено: отсутствует в окружении дочернего |
| Секрет во временном файле | Не создаётся вовсе |
| Инъекция через имя хранилища | Устранена: путь к `op` и имя хранилища идут позиционными `$1`/`$2`, не подставляются в строку |
| Подмена `sh` и `cat` через `PATH` | Устранена: абсолютные `/bin/sh` и `/bin/cat`. Оба помечены `restricted` — **SIP не даёт их заменить даже root'у** |
| Подмена самого `op` | **Остаётся.** `op` лежит в записываемом пользователем каталоге. Смягчение: путь резолвится один раз и **печатается вам** — `ok op 2.39.0 at /opt/homebrew/bin/op`. Сверьте, что он там, где ожидаете |
| Недиагностируемый сбой | Устранён: показывается сообщение `op`, но удерживается, если содержит любое из передаваемых значений |

### Что остаётся, и это не про транспорт

- **`op` — чужая неограниченная программа с сетью**, и весь ваш кошелёк попадает
  ей на stdin. Наш рантайм её не ограничивает никак. Это свойство самой затеи,
  а не реализации.
- **Секрет держат в памяти три процесса** вместо одного: наш, `cat`, `op`.
  `cat` тривиален и защищён SIP, но это ещё одна копия.
- **Сид уходит на серверы 1Password** в зашифрованном виде и оседает в их
  локальном кеше.

### Чем за это заплачено

Запуск `op` требует `--allow-child-process`, поэтому команда работает при
**5/6** вместо 6/6, и запущенный `op` наш рантайм не ограничивает вообще —
это чужая программа со своими правами и своей сетью. Разница видна:

```sh
npm run prove-sandbox                 # 6/6 denied
npm run op-export                     # 5/6, subprocess ALLOWED
```

Именно поэтому это **отдельная команда**: генерация и мастер сохраняют полную
песочницу, а граница остаётся там, где её видно.

### Что нужно понимать

> **Три доли в одном хранилище — не пороговый бэкап.** Это секрет в одном
> месте, только с видимостью многослойности. Для короткоживущего буфера это
> приемлемо, для хранения — нет.
>
> Запись сама содержит это предупреждение в заметках, а команда печатает
> готовую строку для её удаления. **Удалите её**, как только разложили
> содержимое по местам: доли — в три разных физических места, фразу — на бумагу.
>
> И сид покидает вашу машину: 1Password синхронизирует его на свои серверы
> в зашифрованном виде и расшифровывает на каждом устройстве, где вы
> разблокируете хранилище.

Если вам нужно **хранение**, а не буфер — держите в 1Password **одну** долю
SLIP-39. Ниже порога доля не даёт ничего, и компрометация хранилища тогда
безвредна.

## Почему контейнер и виртуальная машина не помогут

Короткий ответ: **программными средствами защитить вычисление от машины,
которая его исполняет, нельзя.** Контейнеры и гипервизоры изолируют **хост от
гостя**, а нам нужно обратное.

Замер на этой машине: процессы контейнера в `ps` macOS не видны — namespace
работает. Но память ВМ лежит в процессе `com.docker.virtualization` под вашим
UID, и `vmmap` перечисляет **126 читаемых областей** без root.

Технология, которая это действительно решает (AMD SEV-SNP, Intel TDX), на
Apple Silicon недоступна — и даже она не закрыла бы путь вывода: 24 слова надо
показать вам на экране, а экран контролирует хост.

Круг разрывает только устройство **со своим экраном**. Полный разбор со всеми
вариантами и замерами: [docs/ru/THREAT-MODEL.md](docs/ru/THREAT-MODEL.md#почему-ни-контейнер-ни-docker-ни-виртуальная-машина-не-спасают).

## Почему здесь нет графического интерфейса

Коротко: GUI ломает три свойства, которые в этом проекте единственные
**доказываются командой**, а не обещанием.

| Что ломается | Как именно |
|---|---|
| **Проверяемость установки** | `npm ci --ignore-scripts` перестаёт работать: GUI-фреймворки догружают рантайм postinstall-скриптом. Запиненный lock-файл с integrity-хешами теряет смысл. |
| **Песочница** | Electron нужны подпроцессы, воркеры, запись на диск и сеть — ровно то, что запрещает `--permission`. Снять точечно нельзя: `6/6 denied` превратится в `0/6`. |
| **Рантайм** | Webview — это браузер. Мы обосновываем преимущество над iancoleman/bip39 тем, что не работаем в браузере; GUI обернул бы этот аргумент против нас. |

Цена в цифрах: сейчас **5 пакетов, около 2.9 МБ, все одного автора**, и `@scure/bip39`
из них прошёл аудит Cure53. Минимальный
GUI приводит дерево на порядки больше, где не проверял никто ничего.

И довод сильнее технических: интерфейс привлекает именно тех, кто хуже всего
готов выполнить офлайн-процедуру. Он не отключит Wi-Fi, не выключит iTerm2
Instant Replay и не помешает сделать скриншот — он снизит порог входа, не снизив
ни одного реального риска. Тому, кому нужен GUI, честный ответ — аппаратный
кошелёк, а не окно поверх Node-скрипта.

Текстовый интерфейс при этом улучшать можно и нужно — без новых зависимостей.
`--qr` уже сделан именно для этого. Подробнее:
[docs/ru/THREAT-MODEL.md](docs/ru/THREAT-MODEL.md#сознательно-не-реализовано).

## Passphrase — что даёт «25-е слово»

Опциональная строка, которую можно задать при генерации. Технически это **не
слово из словаря**, а произвольный текст, попадающий в соль:

```
seed = PBKDF2-HMAC-SHA512(
         password = мнемоника,
         salt     = "mnemonic" + passphrase,   ← сюда
         iterations = 2048 )
```

### Главное: что происходит, если 24 слова утекли

| | Бумагу нашли, passphrase НЕ задана | Бумагу нашли, passphrase задана |
|---|---|---|
| Что получает нашедший | **Весь ваш кошелёк** | 24 слова и **другой, пустой** кошелёк |
| Что ему нужно ещё | Ничего | Подобрать passphrase |
| Ваши действия | Немедленно переводить средства | Есть время, если passphrase стойкая |

Это **единственное**, что passphrase даёт. Без неё бумага и есть кошелёк:
кто прочитал 24 слова — тот и владелец.

### Насколько это надёжно — измерено

BIP-39 растягивает всего **2048 итерациями PBKDF2**. Это микросекунды, то есть
почти никакой защиты от перебора. Если у атакующего есть ваши 24 слова, он
подбирает passphrase дёшево. Замер на MacBook Pro M5:

```
одно ядро:                    190 попыток/с
8 ядер:                     1 523 попыток/с
GPU-ферма (оценка порядка):~190 000 попыток/с
```

| Passphrase | Бит | Держится |
|---|---|---|
| одно словарное слово | 16.6 | **менее секунды** |
| два **случайных** слова | 25.8 | **3 минуты** |
| три случайных слова | 38.7 | 14 дней |
| **четыре случайных слова** | **51.6** | **~290 лет** |
| пять случайных слов | 64.5 | ~2×10⁶ лет |

Проверьте сами: `2^бит / 2 / 190000` секунд. Биты даны с десятичной именно
для этого — округлив их до целых, вы получите другие числа и решите, что
таблица врёт. Время округлено до одной значащей цифры, потому что темп
перебора — оценка порядка, и три значащие цифры в выводе обещали бы больше,
чем даёт вход.

**«Случайных» здесь означает выбранных жребием, а не головой.** 12.9 бита на
слово — это Diceware: слово, выбранное кубиком из списка в 7776 слов. Четыре
слова, которые вы придумали сами, стоят заметно меньше, и инструмент этого не
увидит: он не знает, откуда вы их взяли.

**Порог — 4 случайных слова.** Инструмент оценивает введённое и предупреждает,
если получилось меньше 50 бит.

### Три вещи, которые надо знать до того, как задавать

**1. Неверной passphrase не бывает.** Любая строка даёт валидный кошелёк.
Опечатка молча откроет другой, пустой — без единого сообщения об ошибке.
Регистр и пробелы значимы:

| passphrase | fingerprint |
|---|---|
| `""` | `0xc185b076` |
| `"dog"` | `0x911c8333` |
| `"Dog"` | `0xe6a3e18f` |
| `"dog "` | `0xf55a7a12` |

**2. MetaMask её не поддерживает.** Задали passphrase — импорт этих 24 слов в
MetaMask откроет **пустой** кошелёк без неё. Выглядит как кража средств.
Поддерживают Ledger, Trezor, Rabby, MyEtherWallet.

**3. Она не восстанавливается ничем.** Забыли — средства потеряны навсегда,
что бы ни было на бумаге. Доли SLIP-39 её тоже не несут.

### Итог

| Ситуация | Ответ |
|---|---|
| Кошелёк для расходов, импорт в MetaMask | **Пустая.** Иначе не откроется |
| Сбережения, бумага в сейфе | Пустая или 4+ слова. Промежутка нет |
| Бумага там, где её могут найти | **4+ случайных слова**, хранить **отдельно** от бумаги |

Короткая passphrase — худший из трёх вариантов: защитить бумагу не может,
а потерять средства при забывании вполне. Подробный разбор:
[docs/ru/ENTROPY.md](docs/ru/ENTROPY.md).

## SLIP-39: резервные доли

Одна бумажка с 24 словами — единая точка отказа, и потерять её вероятнее, чем
стать жертвой любой атаки из нашей модели угроз.

```sh
npm run split -- --shares=2of3            # три доли, любые две восстанавливают
npm run split -- --shares=2of3,3of5       # две независимые группы: любая
                                          # одна группа восстанавливает сама
npm run combine                           # восстановить
```

`npm run split` печатает master fingerprint и адрес индекса 1 **до** того, как
показать доли. Сверьте их с тем, что вы записали при генерации: одно неверно
переписанное слово, прошедшее чек-сумму (примерно 1 из 256), даёт другой
валидный кошелёк, и вы получили бы безупречный бэкап чужого кошелька.

Меньше порога долей не дают **ничего** — не «меньше защиты», а буквально ноль
информации о секрете.

> **Наши доли несут BIP-39 ЭНТРОПИЮ, а не BIP-32 seed.**
> Trezor и эталонный `shamir-mnemonic` трактуют восстановленный master secret
> как seed напрямую. Проверено на официальных векторах: 15 из 15. Из одних и тех
> же долей два прочтения дают **разные кошельки**. Восстанавливайте через
> `npm run combine`.
>
> Совместимость подтверждена измерением, а не заявлена: эталонная реализация
> Trezor читает наши доли и возвращает ровно те же 32 байта.
>
> **Доли не содержат BIP-39 passphrase.** Если вы задали 25-е слово, доли сами
> по себе не восстановят ничего — храните его отдельно.

Модуль `slip39.mjs` **не** имеет второй независимой реализации. Это осознанное
отступление, обоснованное в заголовке файла: вместо неё — 45 официальных векторов
Trezor (15 валидных и 30 обязанных упасть), сверка SHA-256 словаря и восстановление
из **каждого** допустимого подмножества. Именно эти векторы поймали реальный баг в
моей арифметике GF(256): таблицы строились умножением на 2 вместо x+1. Вторая
реализация того же автора повторила бы ту же ошибку и согласилась бы сама с собой.

## Целостность

```sh
npm run build
npm run verify-release -- --trusted-keys=/absolute/independent/key-directory
npm run self-test:verified
```

`verify-release` намеренно проверяет полный скачанный релиз, а не произвольный
checkout исходников. Обязательны bundle, детерминированный архив исходников, SBOM,
provenance, рецепт и три подписи; SEA опционален без `--require-all`. Обычные команды
исполняют прочитанный checkout и предупреждают об этом. Команды `:verified` требуют
успешного release preflight и никогда не откатываются к неподписанным исходникам.

Манифест подписан тремя схемами на трёх разных предположениях стойкости:
**Ed25519**, **ML-DSA-87** (FIPS 204, решётки) и **SLH-DSA-SHA2-128s**
(FIPS 205, только хеш-функции — самое консервативное допущение из доступных).

Подписи псевдонимны. Они доказывают, что артефакт не менялся с момента подписи
владельцем ключей, и **не** говорят, кто это.

Отпечатки публичных ключей (SHA-256 от DER SPKI):

| Схема | Отпечаток |
|---|---|
| `ed25519` | `463c3b401b66d9dd8faf17ec042c9f41ae939745cf081a9babed18aa21cee4aa` |
| `ml-dsa-87` | `4afa05402782d13b99b1a385f1f3bf4afa4da341224a693a27dc116015a16b99` |
| `slh-dsa-sha2-128s` | `73297ec0f483ebe8184783599a3d9627da7febca8645396ecc0e56a5efbf44af` |

`npm run verify-release` печатает их же — сверьте.

**Честная оговорка о замкнутости.** Эта таблица лежит в том же репозитории,
что и артефакты. Тот, кто подменил бы релиз, подменил бы и её. README — всё же
другой файл, чем `dist/SHA256SUMS` и подписи, так что подменить пришлось бы
и то и другое; это лучшее, что достижимо внутри одного репозитория,
но по-настоящему круг разрывает только сверка отпечатков с источником, который
вы получили **иным путём**: из другого зеркала, от знакомого, из закреплённого
сообщения. Если вы видели только этот репозиторий — подпись доказывает
внутреннюю целостность и ничего больше.

**Бинарник вторичен, и это принципиально.** Основной артефакт — читаемый `.mjs`.
Внутри бинарника исходник лежит открытым текстом (`strings` его достаёт), флаги
песочницы патчатся, и `--prove-sandbox` в пропатченной сборке напечатает те же
`6/6`. Самоаттестация артефакта, который контролирует атакующий, не доказывает
ничего. Каждый нативный бинарник **замораживает Node v26.7.0**: каждая будущая CVE в V8
остаётся там до пересборки, тогда как при запуске из исходника патчи приходят через
ваш пакетный менеджер.

На macOS скачанный бинарник карантинится, и Gatekeeper убивает его молча —
exit 137, пустой вывод:

```sh
xattr -d com.apple.quarantine ./heatdeath-darwin-arm64
```
